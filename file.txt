# SOFTWARE REQUIREMENT SPECIFICATION: USER AUTH & DYNAMIC DOCUMENT ATTRIBUTION

## 1. OBJECTIVE
The goal is to develop a secure User Authentication and Audit system that integrates with the existing Resume Upload feature. This system must allow for "Guest-to-User" data migration, ensuring that any resume uploaded anonymously is automatically linked to a user's account once they log in or register.

---

## 2. DATABASE ARCHITECTURE (POSTGRESQL)

### 2.1 Table: users (New)
Stores core user credentials and profile information.
- id: UUID (Primary Key, Default: gen_random_uuid())
- name: VARCHAR(255) (Full Name)
- email: VARCHAR(255) (Unique, Indexed)
- password_hash: TEXT (Hashed using Bcrypt)
- created_at: TIMESTAMP (Default: CURRENT_TIMESTAMP)

### 2.2 Table: login_history (New)
Tracks user sessions for auditing and "Last Login" visibility.
- id: SERIAL (Primary Key)
- user_id: UUID (Foreign Key referencing users.id)
- login_at: TIMESTAMP (Default: CURRENT_TIMESTAMP)
- ip_address: VARCHAR(45) (Optional)

### 2.3 Table: resume_metadata (Existing/Modified)
Modified to support the "Ownership Handshake."
- id: SERIAL (Primary Key)
- user_id: VARCHAR(255) 
    * MUST support both Guest IDs (e.g., 'guest_abc123') and Auth IDs (UUIDs).
- file_path: TEXT
- upload_date: TIMESTAMP

---

## 3. FUNCTIONAL REQUIREMENTS

### 3.1 Unprotected Resume Upload
- The `POST /upload-resume` API must remain open to all users.
- If the request is UNAUTHENTICATED: Store the file with a generated `guest_id`.
- If the request is AUTHENTICATED: Store the file with the user’s `UUID`.

### 3.2 Registration (Minimalist)
- Frontend captures: **Name**, **Email**, **Password**.
- Backend: Hashes password, checks for duplicate emails, and creates the record.

### 3.3 Login & Ownership Handshake
When a user authenticates, the system must perform three simultaneous actions:
1.  **Validate:** Verify credentials against the `users` table.
2.  **Audit:** Insert a new row into `login_history`.
3.  **Claim Data:** If the frontend provides a `guest_id` (from browser storage), the backend must execute:
    UPDATE resume_metadata 
    SET user_id = [Authenticated_UUID] 
    WHERE user_id = [Provided_Guest_ID];

---

## 4. FRONTEND & UI SPECIFICATIONS

### 4.1 Visual Theme
To maintain project continuity, all components must use the established design system:
- **Primary Actions:** Deep Jewel Tones (Emerald, Sapphire, or Ruby) for buttons and progress bars.
- **Surface & Inputs:** Warm Earthy Tones (Ochre, Cream, or Sienna) for form cards, backgrounds, and input borders.

### 4.2 Component Logic
- **Storage:** The frontend must check `localStorage` for an existing `guest_id`.
- **State Transfer:** During the Login/Register API call, the `guest_id` must be passed in the request body.
- **Context:** Upon login, the "Guest" state is cleared, and the UI transitions to "Authenticated" mode.

---

## 5. API ENDPOINTS SUMMARY

| Method | Endpoint | Protection | Description |
| :--- | :--- | :--- | :--- |
| POST | `/auth/register` | Open | Creates new user; captures minimal details. |
| POST | `/auth/login` | Open | Authenticates user; updates `login_history` and `resume_metadata`. |
| POST | `/upload-resume` | Open | Saves resume; assigns `guest_id` or `user_id`. |

---

## 6. SECURITY STANDARDS
- **Encryption:** Use Bcrypt with a salt factor of 12 for password hashing.
- **Integrity:** The Handshake update must only occur inside a verified database transaction.
- **Sanitization:** All inputs (Email/Name) must be sanitized to prevent SQL Injection and XSS.
